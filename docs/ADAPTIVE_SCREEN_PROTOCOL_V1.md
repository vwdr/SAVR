# Adaptive Screen Protocol V1 (two-stage, bounded, GPU 0 only)

Status: **frozen for preparation, awaiting one explicit bounded-launch approval.**
This document freezes schedules, record counts, resource caps, stopping
conditions and the attention-implementation audit. It intentionally does not
embed its own SHA-256: the authoritative pins are generated by
`scripts/freeze_adaptive_launch.py` and recorded in the readiness report
(`reports/ADAPTIVE_SCREEN_READINESS_V1.md`).

## Timing specification (corrected, frozen)

- Fixed-384 and dense-512 run compressed/dense **from query one**.
- Only the adaptive arms run the release's algorithm-required dense startup
  (first 3 queries after each episode reset).
- The **per-arm all-query mean, inclusive of adaptive startup, is the primary
  timing comparison**; warm (queries 1–3) and steady (queries ≥4) means are
  reported separately for adaptive arms.
- 240 timing slots: **16 warmup** rows (2 rounds × 4 arms × 2 frames on
  trajectory 0, excluded from every statistic) + **224 measured**
  (8 trajectories × 4 arms × 7 positions). One 7-query trace per
  (trajectory, arm) on shared per-episode state; positions 1–3 use frame 0,
  positions 4–7 use frame 1 (`offline_camera_inputs.py` exposes only frames
  0,1). `query == position` per trace.

## Stage S0: adaptive qualification on the released checkpoint

- 8 trajectories × frames 0,1 = 16 inputs; **176 exact model calls** (16 ×
  [native + zero plain + zero audited] + 8 × 2 modes × 8 parallel plain/audited
  trace calls), ceiling `model_calls=256`, `seconds=3600`, 23,552 MiB, 256 MiB
  artifacts. Runs first in the single bounded launch; the screen never starts
  if S0 fails or its bound is violated.
- Per input: native dense (audited, SDPA witness ≥1), adaptive-zero plain +
  audited (eager witness **== 0**) on both frames, and a 4-query episode
  (3 dense startup + 1 steady) for `adaptive_75` and `adaptive_50`.
- Gates: hooks neutrality (parallel plain/audited traces with identical query
  numbering); zero-vs-native parity (`hidden/normalized/raw`); structural
  execution contract (retention `512,512,512,384|256`; prune boundary at layer
  3 — layers 0–3 full then layers 4–31 short; with `full` = dense layer-0
  length, post-prune layer length = `full − (512 − retained_visual)` because
  the port keeps `[0] + top_visual + [513..full)` (trailing non-visual tokens
  survive), so lengths are `[full]*4 + [full−512+kept]*28`; kept positions
  equal on every post-prune layer; no cache reuse).
- **Tolerance separation (S0 rule):** `adaptive_zero_tolerance =
  max(2 × zero_pruning_observed, 1e-6)` where `zero_pruning_observed` is the
  largest eager-vs-SDPA gap from the **adaptive-zero (fastv_r=0) parity rows
  only** (dense inputs, both frames). It must be **≤ 1e-3** (frozen ceiling),
  else technical stop. Pruning-induced steady differences are a different,
  shorter computation: recorded separately (`pruning_shift_observed_max`),
  reported as evidence, and **never** used to calibrate, gate, or inflate the
  tolerance.
- The achieved tolerance is the parity bound the screen shadows must satisfy.

## Stage S1: the four-arm screen

- `verify()` re-validates the fixed-compression and contemporary reference
  chains plus the S0 summary **in-session** (structural + `launch.json`
  `config_sha256` binding to the frozen S0 config; S0's output directory is
  created fresh via `mkdir(exist_ok=False)`, so a stale summary cannot satisfy
  the gate).
- Native episodes shadow **3 calls per query**: native, dense-512
  (`≤1e-6`, unchanged), and adaptive-zero (bound = S0-achieved tolerance).
  Each parity row carries `sdpa_calls`/`shadow_sdpa_calls` witnesses for the
  attention audit.
- Triage and analysis are **evidence-only**: `positive_method_result=False`,
  `preference=[]`, no automatic arm selection. The fixed-384 vs adaptive
  tradeoff is recorded for the held manuscript/advisor email decision.
- Analysis buckets timing by regime, clusters the timing bootstrap by
  trajectory, stratifies success differences by suite, and reports
  repeatability-limited baseline concern.

## Attention-implementation audit (user-required)

- Transformers 4.40.1 `LlamaSdpaAttention.forward` (pinned upstream blob
  `b245f276…`) delegates to the manual eager `super().forward()` whenever
  `output_attentions=True`. Numerics and speed therefore differ from fused
  SDPA; any adaptive result must count this cost and bound the gap on the
  real checkpoint — the tiny-model comparison alone is not sufficient.
- Runtime witnesses enforce it: adaptive calls must record zero
  `scaled_dot_product_attention` invocations; native/dense calls ≥ 1 (32 per
  forward). The adaptive-zero arm executes the exact eager path with the exact
  attention overhead, and S0 pins the achieved eager-vs-SDPA gap.
- Audit scoping (frozen): the released `LlamaAttentionDiagnostic` is installed
  only around released-SDPA queries (native, dense-512, fixed-384,
  `output_attentions=False`), where it must observe one record per layer per
  forward. Adaptive queries never run inside it — the release forbids the
  `output_attentions=True` eager fallback they require (`attention-output
  fallback is prohibited`) — so their audit is the zero-SDPA witness plus the
  official capture, and adaptive-zero parity rows report `layers == [32, 0]`.

## Stopping conditions

- Any `require` failure → technical_stop.json + traceback; no retry, no
  automatic fallback, no process reprioritization; report as blocked.
- S0 → S1 chain: S1 aborts if S0 is incomplete, stopped, artifact-hash-
  mismatched, or bound-unsatisfied.
- Resource caps are hard: model calls, episodes, wall seconds, memory
  fraction (23,000/24,576), artifact bytes, one GPU.

## Reporting and server discipline

- TITAN CPU testing is reported exactly as **9 passed, 8 skipped** (never
  "17/17 pass"); the source-parity class is skipped by policy on the pinned
  venv.
- No installs, downloads, or modifications outside `/home/ved/SAVR`; no
  `sudo`; no selection or inspection of shared GPU allocations.
- Provenance: every run records config sha, worker/analyzer identity,
  launch/input-preflight/loaded-runtime JSON, checkpoint inventory checksum,
  timestamps, exit codes.
